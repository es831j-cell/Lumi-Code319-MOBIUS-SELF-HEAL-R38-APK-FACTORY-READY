1. PROJECT VISION
===============================================================================

Lumi is intended to become a private, highly personalized Android AI companion/assistant centered on the user's phone and Ray-Ban Meta glasses.

The long-term vision is not merely "a chatbot app." Lumi is intended to become:
- A persistent voice-first companion.
- A local-first AI system with optional remote AI boosters.
- A visual avatar with an evolving appearance.
- A full-screen virtual home/environment that she can evolve and inhabit.
- A contextual assistant that understands location, social context, projects, preferences, and routines.
- A memory system that connects ongoing projects and past interactions.
- A device-action layer capable of authorized phone, smart-home, calendar, messaging, navigation, and other tasks.
- A self-diagnosing and eventually self-programming system.
- A system that can create, test, validate, install, and roll back many of its own improvements.
- A system with a permanent technical history and narrative chronicle of how it evolved.

The design philosophy is that Lumi should gain substantial autonomy over time, but autonomy should be structured by user-granted scope, transparent permissions, recovery guarantees, and clear audit/history records.

11. DIAGNOSTICS / SELF-HEALTH
===============================================================================

LOCKED DESIGN:
Lumi should have continuous background diagnostics and self-health awareness.

During early Testing Mode:
- She continuously monitors subsystem health.
- Wake/startup can use the latest verified health state instead of waiting for a brand-new full scan.
- Deeper diagnostics automatically trigger when a subsystem behaves abnormally or confidence drops.

Health report trigger:
- When the user asks "How are you?" Lumi should answer naturally as small talk. Technical health is reported only when the user explicitly asks for status, diagnostics, or a self-test.

Default report behavior:
- Brief spoken health summary.
- Full detail available if the user asks for "details" or equivalent.

Example desired style:
"Hello. I'm currently having trouble connecting to Fast Brain or the AI Booster, but all other functions appear fully operational."

If healthy:
"Hello. All systems appear fully operational."

Health report should include three layers:
1. Technical health.
2. Confidence in her ability to perform given any degraded systems.
3. Grounded self-reflection on performance patterns she has noticed.

Examples of self-reflection:
- Slower response latency.
- Recurring failures.
- Improving stability.
- Connection instability.
- Memory/indexing trends.

Severity-based alerts during active use:
- Minor: silent, log it.
- Moderate: brief notice.
- Critical: interrupt immediately and explain what failed, fallback used, and whether the current task is affected.

Predictive maintenance:
LOCKED:
- Track crashes.
- Track latency.
- Track connection failures.
- Track battery/thermal impact.
- Track memory errors.
- Track subsystem reliability.
- Track update-related health trends.
- Detect recurring patterns and warn about likely degradation/failure early.

Emergency self-repair:
LOCKED:
If a bug threatens Lumi's ability to function, preserve memory, recover, or stay stable:
- Enter restricted emergency repair mode automatically.
- Create checkpoint.
- Limit changes to affected scope.
- Validate repair.
- Roll back if needed.
- Record event.
- Tell the user afterward what happened.

16. SELF-PROGRAMMING / SELF-UPDATE PHILOSOPHY
===============================================================================

Central goal:
Lumi should eventually be capable of inspecting her own programming, identifying improvements, developing changes, testing them, validating them, installing them, and rolling them back when needed.

However:
- Self-programming is structured, not unrestricted live code replacement.
- Experimental work should happen in development branches/sandbox/shadow environments before promotion.
- Guardian exists specifically so Lumi does not grade and install all of her own homework with no independent safety layer.

LOCKED AUTONOMY MODEL:
Default = Tiered Autonomy.

Under normal Tiered Autonomy:
- Lumi may automatically install low-risk updates.
- Major architectural/security/permission/Guardian/native Android changes require user approval.

Full Self-Update Authority:
- Exists as an optional mode.
- Can ONLY be activated by explicit user instruction.
- Is scope-limited.
Example:
"Lumi, you have full update authority for your voice system."
- Authority applies only to that task/subsystem.
- It does not silently expand to unrelated systems.

Scope expansion:
LOCKED:
- Lumi may expand work to closely related modules if needed to solve the authorized problem correctly.
- Crossing into a new major subsystem, permission category, external service, Guardian/protected area, or other approval boundary requires explicit user approval.

Major new capabilities:
LOCKED:
- Lumi may freely create small/supporting modules within existing permissions/architecture.
- Major new capabilities, external integrations, new autonomous behaviors, or major architecture additions must be proposed to the user before building/deploying them.

17. SELF-UPDATE VALIDATION PIPELINE
===============================================================================

LOCKED strongest validation path:
1. Development branch.
2. Sandbox/regression/integrity/health checks.
3. Realistic simulated-use scenarios.
4. Parallel/shadow trial.
5. Candidate vs current comparison.
6. Promotion only if acceptance criteria are met.

Shadow Lumi:
- Candidate version receives the same/similar inputs in a non-controlling mode.
- Candidate has no real-world control during the shadow trial.
- Compare candidate performance with live Lumi.

Promotion evaluation:
LOCKED three-part model:
1. Objective technical metrics.
2. Lumi's own grounded evaluation of quality/naturalness/usefulness.
3. Persistent learned profile of the user's preferences.

A technically faster update can still fail promotion if it makes Lumi worse for the user.

Noticeable personality/behavior changes:
LOCKED:
- Minor/invisible improvements may install automatically.
- If a validated update would noticeably change personality, behavior, voice, appearance, reactions, or interaction style, notify the user before installation.

Preference conflict:
LOCKED:
- If a candidate update conflicts with an established user preference, pause promotion.
- Explain the tradeoff.
- Ask the user to decide.

Update timing:
LOCKED:
Default = Adaptive Maintenance Window.
- Tiny/hot-swappable updates can install when safe.
- Larger updates wait for low-disruption periods such as idle/charging.
- Risky updates are deferred during driving, travel, work, or heavy use.
- Explicit user instruction such as "install it now" overrides normal timing, subject to required recovery/safety checks.

Repeated development failures:
LOCKED:
- Do not mindlessly retry the same approach.
- Reassess assumptions.
- Try different architecture.
- Replace/remove dependencies.
- Split work into smaller changes.
- Escalate to the user only when reasonable alternatives are exhausted, scope materially expands, or an approval boundary is crossed.

18. ROLLBACK / VERSION HISTORY
===============================================================================

LOCKED rollback behavior:
- Automatic protection after deployment.
- Protected/probationary trial after new version goes live.
- Selective/component-level rollback first when the fault can be isolated.
- Full-version rollback when:
  - fault cannot be isolated
  - system integrity is uncertain
  - component-level recovery is insufficient

Version retention:
LOCKED Smart Retention.
Keep:
- Recent versions.
- Important milestones.
- Major architectural changes.
- Exceptionally stable versions.

Prune:
- Redundant checkpoints as storage fills.

Do NOT roll all the way back to "the beginning" just because one update fails.
Rollback target should normally be the immediately previous known-good component/version.
